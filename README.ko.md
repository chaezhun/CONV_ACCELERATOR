# CNN 컨볼루션 가속기

> 3채널 5×5 stride-3 컨볼루션을 RTL부터 GDS까지 완주한 설계.

합성, 배치, 클럭 트리, 배선을 모두 거쳐 나온 물리 설계다. 기준 설계와 비교해 순위를
매기는 공식으로 채점되는데, 그 공식을 직접 측정해 보니 점수의 대부분이 전력에 있었다.
버퍼 구조를 다시 짜서 **채점 면적을 295,842 µm²에서 106,234 µm²로 2.8배** 줄였고,
기능 검증 필터 3종 모두 1024/1024 일치를 확인했다.

## 배경

```
Score = Δpower + Δarea + 2 × Δtiming        (낮을수록 우수)
Δ = (내 설계 − 기준) / 기준
```

사이클 수는 점수가 아니다. **관문**이다. 필터 3종이 전부 100% 일치해야 하고, 평균
사이클이 450,000 미만이어야 하며, 배선이 성공해야 한다. 하나라도 못 지키면 0점이다.

여기서 직관이 뒤집힌다. 관문을 넘은 뒤로는 빨라져도 보상이 없으므로, 이기는 설계는
**관문만 통과하는 가장 작고 저전력인 것**이다. 기준 설계는 버퍼가 아예 없어서, 버퍼를
쓰는 설계는 면적에서 손해를 안고 시작해 그것을 되갚아야 한다.

공식을 읽는 것만으로는 부족했다. 기준 설계를 직접 측정하니 점수가 어디에 있는지가
보였다.

| 항 | 기준값 | 영향 |
|---|---|---|
| 면적 | 5,760 µm² | Δarea ≈ 17.6 |
| **전력** | **0.0070 W** | **Δpower ≈ 15.4 — 0.007로 나누므로 1 mW가 0.14점** |
| 타이밍 | 1.0 ns | 2 × Δtiming ≈ 0.04 |

타이밍은 가중치 2를 달고도 기여가 거의 없다. 순위를 가르는 것은 전력이다. 눈에 보이는
가중치만 보고 타이밍에 매달렸다면 방향을 잘못 잡았을 것이다.

## 설계

메모리 읽기가 10사이클이고 파이프라인이 불가능하므로, 데이터를 버퍼에 담아 재사용하지
않으면 사이클 관문에 도달할 수 없다.

### 채널 직렬화 + 외부 RAM 부분합 누적

3채널을 전부 버퍼링하면 1,470바이트가 필요하고 이것이 면적을 지배했다. 채널을 하나씩
처리하며 부분합을 피처 RAM에 누적(첫 패스는 쓰기, 이후는 읽기-덧셈-쓰기)하면 버퍼가
495바이트로 줄고 부분합 레지스터가 아예 사라진다.

| 버전 | 구조 | 채점 면적 |
|---|---|---:|
| v11 | 3채널 동시 버퍼 (1,470 B) | 295,842 µm² |
| **v12** | **채널 직렬 + 외부 RAM 누적 (495 B)** | **106,234 µm²** |

읽기 횟수가 같으므로 사이클은 그대로다. 행 단위 rolling 재사용으로 출력 행이 하나
진행될 때 5행 중 3행만 새로 읽는다.

### 뱅킹된 라인 버퍼

1,470바이트를 단일 배열로 두었더니 합성기가 메모리로 인식하지 못하고 1470:1
멀티플렉서와 플립플롭 11,760개로 풀어버려 배선 위반 13,224건이 났다. 행 슬롯별
5뱅크(각 99바이트)로 나누자 각 뱅크가 512바이트 추론 한계 아래로 들어가고, 읽기 mux가
495:1에서 5:1로 줄고, 인덱스 계산에서 곱셈이 사라졌다. 이후 배선이 DRC 위반 0으로
통과했다.

### 진단을 반증한 과정

필터 3종 중 하나가 특정 인덱스부터 계속 틀렸다. 기존 설명은 "테스트벤치의 race
condition이라 RTL로는 못 잡는다"였고, 그 가정 위에 코드가 쌓여 있었다.

원본 바이너리로 컨볼루션을 Python에서 직접 다시 계산하니 결론이 났다.

```
Σ over ch,dr,dc:  ifmap[ch][3R+dr][3C+dc] × filter[ch][dr][dc]
    → 정답 파일과 1024 / 1024 일치
```

race도 특수 규칙도 없었다. 진짜 원인은 둘 다 내 쪽에 있었다.

1. 메모리가 직전 사이클의 주소를 잡으므로 읽을 때 `col = 3C+dc+1` 보정이 필요
2. 출력 열 31은 입력 열 97이 필요한데, 보정 후 버퍼 위치 98에 놓인다. 98칸짜리 버퍼의
   한 칸 밖이라 다음 행 값을 읽고 있었다

다른 두 필터가 통과했던 건 그 위치의 가중치가 우연히 0이었기 때문이다. 버퍼 폭을 98에서
99로 한 칸 늘리자 셋 다 통과했고, 그동안 쌓인 우회 코드를 전부 걷어냈다.

### 임계 경로의 종점을 쫓아간 타이밍 개선

병목을 짐작하지 않고, 물리설계 리포트가 지목하는 **종점(endpoint)** 을 매번 확인한 뒤
그 경로만 끊었다. 그러자 병목이 세 번 옮겨 다녔다.

| 버전 | 임계 경로 종점 | 경로 성격 | 여유(WNS) |
|---|---|---|---:|
| v13 | MAC 입력 버퍼 | 카운터 → 495:1 버퍼 mux → MAC 입력 (**반 클럭**) | −0.27 ns |
| v14 | 부분합 레지스터 | 부분합 가산기 → 선택 mux → 레지스터 (**한 클럭**) | −0.01 ns |
| **v15** | **MAC 내부 누산기** | 8×8 곱셈 + 16비트 누적 (**수정 불가 모듈**) | **−0.02 ns** |

v14는 큰 읽기 mux의 결과를 레지스터에 한 번 담아 반 클럭 경로를 한 클럭으로 늘렸다.
데이터가 한 사이클 늦어지는 것은 채우기 구간에서 누적을 끄고 마지막에 배출 사이클을
하나 더 두어 보정했다.

v15는 남아 있던 부분합 출력 mux를 없앴다. 첫 패스에서 `feat_old`가 항상 0이 되도록
리셋값을 잡으면(첫 패스는 읽기 상태를 거치지 않는다) 조건 분기가 필요 없어져
**항상 `feat_old + mac_result`** 로 통일된다. mux가 사라지면서 면적과 전력도 함께 줄었다.

마지막 종점은 **수정이 금지된 MAC 모듈 안**이다. 1 GHz에서 단일 사이클 곱셈-누적이 갖는
구조적 한계이므로, 내가 손댈 수 있는 범위의 최적화가 끝났다는 것을 리포트로 보일 수 있었다.

### 물리 파라미터 2차원 탐색

Part 2는 RTL을 고정한 채 파라미터만 조정한다. 채점 면적이 `설계면적 / 배치밀도`이므로
밀도를 축으로 잡았다.

**배치 밀도 (클럭 1.0 고정)** — U자 곡선이 나온다.

| 밀도 | 채점 면적 | 전력 | 타이밍 여유 | 점수 |
|---:|---:|---:|---:|---:|
| 40 (기준) | 5,760 | 0.00700 | 0 | 0 |
| 60 | 3,850 | 0.00644 | 0 | −0.412 |
| **80** | **2,851** | **0.00630** | 0 | **−0.605** |
| 85 | 2,721 | 0.00732 ↑ | −0.05 ↓ | −0.382 (악화) |
| 90 | — | — | — | **배치 실패** |

85 이상에서는 혼잡으로 전력과 타이밍이 나빠져 면적 이득을 넘어선다. 80이 최소점이고,
셀 면적 하한(약 2,452 µm²)에 근접한 값이다.

**클럭 주기 (밀도 80 고정)**

| 클럭 주기 | 타이밍(=주기−여유) | 전력 | 점수 |
|---:|---:|---:|---:|
| 0.9 | 1.0 | 0.00935 | −0.166 |
| **1.0** | **1.0** | **0.00630** | **−0.605** |
| 1.2 | 1.2 | 0.00476 | −0.423 |

어느 쪽으로 움직여도 손해다. **조이면** MAC이 지연 한계라 더 빨라지지 못하고 타이밍은
1.0에 고정된 채 셀만 커져 전력을 48% 낭비한다. **풀면** 여유가 0에서 멈추고 타이밍이 곧
클럭 주기가 되어 1.2로 올라간다. 전력은 32% 줄지만 가중치 2의 페널티가 이를 넘는다.

즉 타이밍의 최솟값은 실제 경로 지연(≈1.0)이고, **그것을 최저 전력으로 달성하는 지점이
여유가 정확히 0이 되는 클럭 1.0**이다.

전력 회수·클럭 트리·셀 제한도 전수 확인했지만, **전력의 73%가 수정 불가한 MAC 곱셈기**에서
나와 회수할 여유가 없었다(전력 회수 옵션 적용 시 변화 0). 유효한 레버가 밀도와 클럭
둘뿐임을 확인하고 탐색을 끝냈다.

### 검증을 네 단계로 나눈 이유

| 단계 | 방법 | 확인 내용 |
|---|---|---|
| 1. 정답 정의 | Python 역산 (`reverse.py`) | 정답 파일이 표준 컨볼루션인가 — 1024/1024 |
| 2. 아키텍처 | Python 모델 (`verify_b1.py`) | 채널 직렬 + 16비트 modular 누적이 정답과 같은가 — **RTL 작성 전** |
| 3. 기능 | NCverilog | 필터 3종 각 1,024개 출력 전부 일치 + 사이클 측정 |
| 4. 물리 | OpenROAD | 합성 → 배치 → 배선 완주, DRC 0, 면적·전력·타이밍 추출 |

2단계가 실제로 값을 했다. 채널을 나눠 16비트로 누적해도 정답과 같은지를 **RTL을 짜기
전에** 확인해 뒀기 때문에, 구조를 바꾼 뒤 값이 틀리면 원인이 구현 실수임을 바로 알 수 있었다.

## 결과

| | |
|---|---|
| 기능 | 필터 3종 **각 1024 / 1024** |
| 사이클 | **435,778** (관문 450,000) |
| 배선 | 통과, **DRC 위반 0** |
| 채점 면적 | 107,341 µm² |
| 타이밍 여유 | −0.02 ns |
| 전력 | 0.115 W |
| Part 1 점수 | **33.1** (41.3에서) |
| Part 2 점수 | 기준 대비 **−0.605** (면적 −50%, 전력 −10%) |

Part 1의 개선은 타이밍이 아니라 거의 전부 전력(0.170 → 0.115 W)에서 나왔다.

Part 2는 RTL을 고정한 채 물리 파라미터만 조정했다. 배치 밀도와 클럭 주기를 2차원으로
탐색했고, 밀도 80 · 클럭 1.0 ns가 U자 곡선의 최저점이었다. 그보다 낮으면 다이가 커지고,
높으면 혼잡으로 인한 전력·타이밍 손해가 면적 이득을 넘어선다.

## 빌드와 실행

**사전 조건** — OpenROAD Flow Scripts, Nangate45 PDK, 기능 시뮬레이션용 NCverilog.

```bash
# 기능 시뮬레이션
ncverilog part1_rtl/Convolver.v part1_rtl/MAC.v <testbench>

# 물리 설계 — config.mk와 constraint.sdc를 플로우 디렉터리에 배치한 뒤
make DESIGN_CONFIG=./config.mk
```

`verification/`의 Python 골든 모델로 정답 파일을 재생성해 RTL 출력과 대조할 수 있다.

## 참고

**배포물** — `part1_rtl/MAC.v`는 수업 배포 파일이며 수정 금지 조건이 붙어 있다. 빌드가
되도록 하기 위해 그대로 동봉했다. 그 밖의 코드는 전부 직접 작성했다.

**미포함** — 테스트벤치(`tb_Convolver.v`)와 물리설계 플랫폼 설정도 수업 배포물이라 넣지
않았다. 위 시뮬레이션 명령의 `<testbench>` 자리에 해당한다.
